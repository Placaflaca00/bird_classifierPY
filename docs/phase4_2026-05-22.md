## TL;DR

Fase 4 quedó **deployada en producción** end-to-end. El usuario puede:

1. Subir un audio en el HF Space.
2. Tildar consent opt-in para entrenamiento.
3. Recibir una predicción con indicador de cuota (escalating 10/5/1).
4. Dar feedback: 👍 confirma, 👎 → grid de 19 especies (excluye la predicha) → corrected; o "Esto no era un pájaro" → rejected_as_non_bird.

Todo se persiste en DynamoDB. La capa human-in-the-loop (`review_status="pending"`) está **blindada con tests** contra regresión silenciosa: ningún path de feedback modifica `review_status`, garantizando que audio entra a training solo tras revisión humana (Fase 5, futura).

**Endpoint público**: https://huggingface.co/spaces/placaflaca/bird-classifier-py

## Lo que salió mal y cómo se arregló

### 🔴 Bloqueador: disco C: lleno (0 bytes libres)
- **Síntoma**: `pytest` falla escribiendo cache; `git commit` riesgoso.
- **Fix**: borré ~13.7 GB de cachés regenerables (Cypress, Postman, Postman-Agent, npm-cache, .gradle/caches, Temp). Docker preservado.
- **Lección**: el verdadero hog era `System Volume Information` (System Restore points, no medibles sin admin). Atajo: `cleanmgr` "Limpiar archivos de sistema" o `SystemPropertiesProtection` para reducir el cap.

### 🔴 Docker Desktop "no abre" post-disk-full
- **Síntoma**: procesos zombie de Docker arriba (PIDs antiguos), GUI no aparece al clickear el shortcut.
- **Fix**: kill `Docker Desktop`, `com.docker.backend`, `com.docker.build` + `wsl --terminate docker-desktop` (NO `--shutdown`, que mata el Ubuntu del user) + relanzar `Docker Desktop.exe`.
- **Lección**: cuando el disco se llena con Docker corriendo, su estado en memoria queda corrupto.

### 🟡 ECR login timeout transitorio
- **Síntoma**: `Get https://...ecr...:/v2/: context deadline exceeded` en el primer `docker login` post-restart.
- **Fix**: reintentar al siguiente comando. Funcionó al segundo intento sin cambios.
- **Lección**: Docker network del daemon recién booteado tarda algunos segundos extras. No es bug, es transitorio.

### 🟡 `client.py` requiere `api_url` con sufijo `/predict`
- **Síntoma**: smoke API devolvió `error_kind='config'` (404) cuando pasé `https://...prod` sin `/predict`.
- **Causa**: `client.py` deriva `/upload-url` y `/feedback` **reemplazando** el segmento `/predict`. Sin ese sufijo, el POST va al base y obtiene 404.
- **Fix**: pasar URL completa terminando en `/predict`.
- **Lección**: documentado in-line en `app/client.py:17`. Para próximos smokes: respetar la convención del cliente.

### 🟡 Cold start /predict 90s (primera invocación)
- **Síntoma**: warmup vía `/upload-url` (4s) no calentó el code path de ML; primera llamada a `/predict` tomó 90s.
- **Causa**: BirdNET TFLite se carga lazy en el primer `/predict`, no en el init del handler.
- **Fix**: smoke usó warmup directo de `/upload-url`; la lentitud de la primera llamada a `/predict` no es bug.
- **Lección**: para smoke tests post-deploy, warm directo del code path que vas a medir (no asumir que cualquier endpoint calienta todo).

### 🟢 Falsos positivos a aclarar
- **Lambda `Environment.Variables: null`** — no es bug. Tabla DDB hardcoded en `handler.py:76`. Si en el futuro pasamos a env var, agregar al rebuild del Lambda.
- **HF `.env` con `HF_TOKEN=` vacío** — no es bug. `huggingface_hub` autentica por cache (`~/.cache/huggingface/token` de `huggingface-cli login`).
- **`consent=False` en items del browser** — esperado. Checkbox arranca unchecked, el usuario debe tildarlo activamente para `consent=True`.
